# Бэкап и восстановление БД

БД в проде — PostgreSQL на Neon (serverless). Neon сам хранит историю изменений
для point-in-time restore, но это восстановление внутри того же Neon-аккаунта:
если аккаунт удалён/скомпрометирован или нужен снапшот вне Neon — своей копии
нет. Поэтому дополнительно настроен независимый ежедневный бэкап.

## Как это работает

`.github/workflows/db-backup.yml` каждый день в 02:00 UTC (и вручную через
"Run workflow" в GitHub Actions):

1. `pg_dump` по `DATABASE_URL` → `dump.sql.gz`
2. Шифрует симметрично GPG (`BACKUP_GPG_PASSPHRASE`) → `dump.sql.gz.gpg`
3. Загружает как asset в GitHub Release с тегом `backup-YYYY-MM-DD-HHMM`
4. Удаляет релизы старше 30 дней

Дамп никогда не попадает в git-историю (это Release asset, не коммит), и
зашифрован — даже если репозиторий когда-нибудь станет публичным или к нему
получит доступ третье лицо, сами данные (пароли клиентов — хэши, телефоны,
адреса) не будут доступны без пассфразы.

## Что нужно настроить один раз (руками, я это сделать не могу — нет доступа к GitHub/Neon)

В настройках репозитория `Online-Store_back` → Settings → Secrets and
variables → Actions → New repository secret:

- **`BACKUP_DATABASE_URL`** — строка подключения к Neon в формате
  `postgres://user:password@host/dbname?sslmode=require`. Лучше создать в
  Neon отдельную read-only роль специально для бэкапов (Neon → Roles →
  Create role), чтобы утечка секрета не давала прав на запись.
- **`BACKUP_GPG_PASSPHRASE`** — любая длинная случайная строка
  (например `openssl rand -base64 32`). Сохраните её также в менеджере
  паролей — без неё расшифровать бэкапы будет невозможно.

Без этих двух секретов workflow будет падать на первом шаге с понятной
ошибкой (не тихо проглатывать проблему).

## Восстановление

1. Скачать нужный asset (`dump.sql.gz.gpg`) со страницы Releases репозитория.
2. Расшифровать и распаковать:
   ```bash
   gpg --batch --passphrase "$BACKUP_GPG_PASSPHRASE" -d dump.sql.gz.gpg | gunzip > dump.sql
   ```
3. Накатить на целевую БД (новую ветку Neon или локальный Postgres для
   проверки — НЕ сразу в прод):
   ```bash
   psql "$TARGET_DATABASE_URL" -f dump.sql
   ```
4. Проверить целостность (количество строк в ключевых таблицах: products,
   orders, users) перед тем как переключать прод на восстановленную БД.

## Ограничения текущего решения

- Ретеншн 30 дней — старые бэкапы удаляются автоматически. Если нужна более
  долгая история (например для бухгалтерии/аудита за годы), стоит завести
  отдельный "архивный" tag/repo без авто-удаления.
- Расписание зависит от доступности GitHub Actions — это внешний сервис вне
  инфраструктуры проекта (Fly/Neon), что и есть смысл независимого бэкапа.
- Восстановление ручное (запуск `psql` руками) — при реальном инциденте это
  единственный шаг, который стоит когда-нибудь автоматизировать/расписать
  подробнее, если появится второй похожий случай.
